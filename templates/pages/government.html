{{ t "page.government.shapeOfTheState" "The shape of the state" }}

{{ tHTML "page.government.hierarchyIntro" "The Staatskalender is a single tree held together by schema:parentOrganization, and its top level is the Swiss constitutional order laid out as data. The Federal Council sits at the head of seven departments plus the Federal Chancellery; the federal courts — Supreme, Administrative, Criminal and Patent — stand beside it rather than beneath it, as the separation of powers requires; and the cantons form their own branch alongside the Confederation." }}

{{ tHTML "page.government.departmentsIntro" "Counted by everything beneath them, the departments are strikingly uneven. Defence is by far the largest — it carries the whole army structure, which is why a department with a modest headquarters expands into thousands of units. The Chancellery, which coordinates the government rather than delivering services, is the smallest by an order of magnitude." }}

# ?dept stays an IRI so the backend resolves the department name and links it. # # parentOrganization+ is TRANSITIVE on purpose: it counts every descendant at any # depth, not just direct children. That is what makes Defence's army structure show # up. A non-transitive count would report single digits for every department and # say nothing. # # The name is fetched in an OUTER pattern rather than inside the aggregate, and # filtered to one language — Staatskalender names carry de/fr/it tags, so an # unfiltered ?name multiplies each row three times. SELECT ?dept ?units WHERE { { SELECT ?dept (COUNT(?descendant) AS ?units) WHERE { GRAPH <https://lindas.admin.ch/fch/staatskalender> { <https://register.ld.admin.ch/staatskalender/organization/10000000> schema:subOrganization ?dept . ?descendant schema:parentOrganization+ ?dept . } } GROUP BY ?dept } } ORDER BY DESC(?units)

{{ tHTML "page.government.topLevelIntro" "Above the departments sit the bodies that answer to no one inside the administration. Listing the organisations with no parent at all gives the constitutional top of the tree in one query — the government, the four federal courts, the prosecution service and its supervisory authority, the parliamentary services, and the cantons." }}

# "No parent" is the definition of a top-level body here, expressed as # FILTER NOT EXISTS. ?children counts DIRECT members only (no +), because at this # level the interesting figure is how the body itself is subdivided. SELECT ?org ?children WHERE { { SELECT ?org (COUNT(?child) AS ?children) WHERE { GRAPH <https://lindas.admin.ch/fch/staatskalender> { ?org a schema:GovernmentOrganization . ?child schema:parentOrganization ?org . FILTER NOT EXISTS { ?org schema:parentOrganization ?anyParent } } } GROUP BY ?org } } ORDER BY DESC(?children)

{{ t "page.government.peopleInRoles" "People, and the roles they hold" }}

{{ tHTML "page.government.rolesIntro" "A person is never attached to an office directly. Between them sits an OrganizationRole — a small resource naming the function, pointing at the person with schema:member and at the unit with schema:memberOf. It is a modelling choice worth noticing: because the role is its own resource, one person can hold several distinct functions in several bodies without any of them being confused, and the function itself (Mitglied, Direktor, Juge fédéral suppléant) is data rather than a label buried in a string." }}

{{ tHTML "page.government.federalCouncilNote" "Query it for the Federal Council and you get the seven sitting members by name, each through a role called simply Mitglied. The same pattern retrieves the judges of every federal court and the directors of every office." }}

# People carry givenName/familyName — NOT schema:name. A ?person schema:name pattern # matches nothing at all here and returns an empty table. # # ?org stays an IRI so the backend resolves and links the unit. Role names carry # language tags, so dispLang keeps one row per role instead of three. SELECT ?familyName ?givenName ?roleName ?org ?person WHERE { GRAPH <https://lindas.admin.ch/fch/staatskalender> { ?role a schema:OrganizationRole ; schema:member ?person ; schema:memberOf ?org ; schema:name ?roleName . ?person schema:givenName ?givenName ; schema:familyName ?familyName . FILTER (lang(?roleName) = "de") } } ORDER BY ?familyName ?givenName
{{ template "sparqlAsyncTable" (dict "queryId" "govRoles" "title" (t "card.rolesAndHolders" "Roles and the people holding them") "icon" "users" "collapsed" true) }}

{{ tHTML "page.government.rolesCaveat" "Role names are filtered to German here so each role appears once; the same resources carry French and Italian names, and opening a role shows all of them. Note also that only around half the people in the directory have a recorded gender and only a subset a direct telephone number — the register is a directory of functions first and of individuals second." }}

{{ t "page.government.throughTime" "The administration through time" }}

{{ tHTML "page.government.versioningIntro" "The organisation graph is the most unusual model in this theme, and possibly on the whole platform. It does not describe the administration as it is; it describes every state the administration has been in. Each unit has a stable identity, and hanging off that identity is a chain of dated versions, each with a start date, an end date, and predecessor and successor links to its neighbours in time." }}

{{ tHTML "page.government.versioningConsequence" "The consequence is that most of what this graph contains is deliberately historical: the large majority of versions are marked deprecated, because they have been superseded. That is the point rather than a defect. When an office is renamed or absorbed, the old version is not overwritten — it is closed with an end date and linked to what replaced it, so a reference from a document written in 2015 still resolves to the body that existed then." }}

# ?identity stays an IRI so the backend resolves the unit's current name and links it. # # Counts how many dated versions each organisational identity has accumulated — # a direct measure of how often that unit has been renamed or restructured. # Bounded with HAVING so the table shows the genuinely churn-heavy units rather # than 20,000 rows of "1 version, never changed". SELECT ?identity ?versions ?firstStart ?lastEnd WHERE { { SELECT ?identity (COUNT(?v) AS ?versions) (MIN(?start) AS ?firstStart) (MAX(?end) AS ?lastEnd) WHERE { GRAPH <https://lindas.admin.ch/fch/organization> { ?v a <https://version.link/Version> ; <https://version.link/identity> ?identity ; schema:startDate ?start . OPTIONAL { ?v schema:endDate ?end } } } GROUP BY ?identity HAVING (COUNT(?v) > 3) } } ORDER BY DESC(?versions)
{{ template "sparqlAsyncTable" (dict "queryId" "govVersionsPerIdentity" "title" (t "card.mostRevisedUnits" "Most frequently revised organisational units") "icon" "history" "collapsed" true) }}

{{ tHTML "page.government.versioningCaveat" "A high version count is not a sign of instability so much as of granular record-keeping — an address change or a corrected abbreviation creates a version just as a merger does. Note too that this graph uses ld.admin.ch/ou/ IRIs while the Staatskalender uses register.ld.admin.ch/staatskalender/organization/: they describe the same administration but are not the same resources, and they do not join on the IRI." }}

{{ t "page.government.termdat" "Saying the same thing in four languages" }}

{{ tHTML "page.government.termdatIntro" "A federal state with four official languages has a problem no monolingual administration faces: every law, form and press release must exist in German, French and Italian, and the words must mean exactly the same thing in each. TERMDAT is the Chancellery's answer — the terminology database of the federal administration, and the largest such resource in the country." }}

{{ tHTML "page.government.termdatStructure" "The model puts the concept first, not the word. An entry is a concept; the terms in each language hang off it through schema:hasPart, each with a position marking whether it is the preferred term or a permitted variant. That inversion is what makes the database work as a translation aid: the Freedom of Information Act is one entry carrying BGÖ, LTrans, LTras and FoIA as four names for a single thing, rather than four separate records hoping to be matched. The table further down shows exactly that, for every federal act abbreviated in all four languages." }}

{{ tHTML "page.government.termdatStatus" "Entries also carry their editorial state. Most are validated — checked and approved by the Terminology Section — while others are marked in progress or deprecated, so a query can restrict itself to the terminology that is actually authoritative. Many entries add a definition with a citation of the legal act it comes from, which turns the database into a route from a word back to the article of law that defines it." }}

# ?domain stays an IRI so the backend resolves and links the subject field. # # Terms attach to a SUB-domain, which is schema:isPartOf a domain — the one-hop # pattern (?t domain ?domain) matches nothing and returns zeros for every row. # The two-hop path through ?sub is required. SELECT ?domain ?terms WHERE { { SELECT ?domain (COUNT(?t) AS ?terms) WHERE { GRAPH <https://lindas.admin.ch/fch/termdat> { ?t <https://schema.ld.admin.ch/termDomain> ?sub . ?sub schema:isPartOf ?domain . ?domain a <https://schema.ld.admin.ch/TermDomain> . } } GROUP BY ?domain } } ORDER BY DESC(?terms)
{{ template "sparqlAsyncTable" (dict "queryId" "govTermDomains" "title" (t "card.terminologyDomains" "Terminology by subject field") "icon" "book-open") }}

{{ tHTML "page.government.termdatLawNote" "Law dominates the collection by a wide margin, with politics a distant second — an accurate picture of what the Confederation most often needs to translate precisely. Below them the subject fields track the rest of this site almost exactly: agriculture and forestry, environment, medicine, finance, transport." }}

# The four-language join, done the cheap way. # # A term resource holds ALL FOUR language literals on the SAME node — the language # lives in the literal tag, not in separate resources. So this is one node with four # filtered names, not a four-way self-join. # # Joining four separate ?termDe/?termFr/?termIt/?termEn nodes through hasPart is the # obvious formulation and it TIMES OUT on this graph: ~35k entries × the cross # product of their parts. Don't reintroduce it. # # Abbreviations are used here because they are the clearest demonstration — the same # federal act named four ways (BGÖ / LTrans / LTras / FoIA). SELECT ?de ?fr ?it ?en ?entry WHERE { GRAPH <https://lindas.admin.ch/fch/termdat> { ?term a <https://schema.ld.admin.ch/Abbreviation> ; schema:name ?de, ?fr, ?it, ?en . ?entry schema:hasPart ?term ; a <https://schema.ld.admin.ch/ValidatedEntry> . FILTER (lang(?de) = "de") FILTER (lang(?fr) = "fr") FILTER (lang(?it) = "it") FILTER (lang(?en) = "en") } } ORDER BY ?de
{{ template "sparqlAsyncTable" (dict "queryId" "govFourLanguages" "title" (t "card.fourLanguageTerms" "Federal act abbreviations in four languages") "icon" "languages") }}

{{ tHTML "page.government.fourLanguagesCaveat" "Only entries carrying an abbreviation in all four languages appear here; a great many concepts are recorded in the three national languages without an English equivalent, and those are absent from this table rather than incomplete. English is a working addition to TERMDAT, not an official language of the Confederation — which is why some rows repeat the French form in the English column when no separate English abbreviation exists." }}
