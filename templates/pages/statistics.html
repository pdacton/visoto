{{ t "page.statistics.aboutThisTheme" "About this theme" }}

{{ tHTML "page.statistics.intro" "This theme is the substrate. Nothing here is a measurement of the world — it is the machinery that lets measurements be compared: which municipality a figure belongs to, which occupation a person was recorded as having, which industry code a business falls under. Every other page on this site depends on it, usually without saying so." }}

{{ tHTML "page.statistics.twoProblems" "Two problems dominate, and the two main graphs each solve one. Reference data changes — municipalities merge, and a statistic about Wald in 2005 is not about the same territory as one from 2025. And reference data must be shared — if the health office and the labour office each invent their own occupation codes, their figures can never be joined. The Federal Statistical Office answers both, with a versioned municipality register and the I14Y interoperability platform." }}

{{ tHTML "page.statistics.registersToo" "Alongside them sit the registers of things that exist rather than codes: the Zefix commercial register from the Federal Office of Justice, naming every legal entity in the country, and the territorial resources that cube observations across the platform resolve into." }}

{{ t "page.statistics.theMunicipalities" "Three and a half thousand municipalities" }}

{{ tHTML "page.statistics.municipalitiesIntro" "The municipality is the atom of Swiss statistics: almost every figure the Confederation publishes is either reported per municipality or aggregated up from them. The register defines the full three-level hierarchy — canton, district, municipality — and the shape is uneven in ways that reflect history rather than population. Bern and Vaud each carry hundreds of communes; Graubünden has more districts than Zurich has, for a fraction of the people." }}

# ?canton stays an IRI so the backend resolves the canton name and links it. # # The hierarchy is TWO hops: municipality -> district -> canton via schema:isPartOf. # There is no direct municipality-to-canton edge, and a containedInPlace* path does # NOT reach the canton either — it stops at the district. Use isPartOf twice. SELECT ?canton ?municipalities ?districts WHERE { { SELECT ?canton (COUNT(DISTINCT ?m) AS ?municipalities) (COUNT(DISTINCT ?d) AS ?districts) WHERE { GRAPH <https://lindas.admin.ch/fso/register> { ?m a <https://schema.ld.admin.ch/PoliticalMunicipality> ; schema:isPartOf ?d . ?d schema:isPartOf ?canton . ?canton a <https://schema.ld.admin.ch/Canton> . } } GROUP BY ?canton } } ORDER BY DESC(?municipalities)
{{ template "sparqlAsyncTable" (dict "queryId" "statsMunicipalitiesPerCanton" "title" (t "card.municipalitiesPerCanton" "Municipalities and districts per canton") "icon" "map") }}

{{ tHTML "page.statistics.municipalitiesCaveat" "Municipalities also carry a geosparql:hasGeometry link to their boundary polygon in geo.ld.admin.ch, and a GeoNames feature code — so the register is a bridge into mapping data as well as a list of names. Not every municipality has a geometry attached; the coverage is partial." }}

{{ t "page.statistics.theGreatMerging" "The great merging" }}

{{ tHTML "page.statistics.mergersIntro" "Switzerland had over 3,000 municipalities for most of the twentieth century and has been steadily losing them ever since — not through any federal policy but through thousands of local decisions to merge. The register records every one of these as a change event, with the predecessors that went in, the successor that came out, and the date it took effect. This is the same version.link model the federal administration uses for its own reorganisations." }}

{{ tHTML "page.statistics.mergersWaves" "Grouped by year, the mergers arrive in waves rather than a trickle. The cantons drive them — a canton offers financial incentives, and dozens of communes merge in a single January. 2006 and 2010 stand out sharply, each absorbing over four hundred municipalities into successors. Because every merger takes effect on 1 January, the whole map of Switzerland changes on one day each year." }}

# ?absorbed counts PREDECESSOR links, not events: one event can absorb several # municipalities at once, so the two columns diverge — and the gap between them is # itself informative (2009 shows 114 absorbed across only 32 events). # # The year is parsed from the validFrom string with SUBSTR rather than compared as # a typed date, which keeps the GROUP BY cheap. String comparison is safe here # because YYYY-MM-DD sorts chronologically. SELECT ?year ?events ?absorbed WHERE { { SELECT ?year (COUNT(DISTINCT ?ev) AS ?events) (COUNT(?pred) AS ?absorbed) WHERE { GRAPH <https://lindas.admin.ch/fso/register> { ?ev a <https://schema.ld.admin.ch/MunicipalityChangeEvent> ; schema:validFrom ?d ; <https://version.link/predecessor> ?pred . BIND (SUBSTR(STR(?d), 1, 4) AS ?year) } } GROUP BY ?year } } ORDER BY DESC(?year)
{{ template "sparqlAsyncTable" (dict "queryId" "statsMergersPerYear" "title" (t "card.mergersPerYear" "Municipality change events per year") "icon" "git-merge") }}

{{ tHTML "page.statistics.mergersCaveat" "Not every change event is a merger — the register uses the same mechanism for renamings, boundary corrections and transfers between districts, so the event count is an upper bound on genuine amalgamations. An event with several predecessors and one successor is the classic merger shape; one predecessor and one successor is usually a rename." }}

{{ tHTML "page.statistics.mergersWhyItMatters" "The practical consequence for anyone querying this platform: a municipality IRI is a version, not a place. If you join a 2005 statistic to a 2026 municipality list on identifier alone, the rows that merged in between will silently vanish. The register exists precisely so that the join can be done properly, by walking the predecessor chain." }}

{{ t "page.statistics.zefix" "Every company in the country" }}

{{ tHTML "page.statistics.zefixIntro" "Zefix — the Central Business Names Index, kept by the Federal Office of Justice — is the register of every legal entity in the Swiss commercial register. At close to 800,000 organisations it is by a wide margin the largest register on this platform, and it is the counterpart to the municipality register: one identifies places, the other identifies the businesses standing in them." }}

{{ tHTML "page.statistics.zefixUid" "Its load-bearing feature is the UID, the company identification number, which every entity carries. That single identifier is what lets a company be recognised across otherwise unrelated datasets — the electricity grid operators in the energy theme carry their UID, and it resolves to the legal entity here. Each entry also holds a legal form from the eCH-0097 standard, a registered address, the municipality of domicile, and in most cases the company's stated purpose in full prose." }}

# ?legalForm stays an IRI so the backend resolves and links the eCH-0097 code. # # Legal forms are a SHARED vocabulary (ld.admin.ch/ech/97/legalforms/…), not strings # local to Zefix — which is why the resolved label works and why the same codes # appear in other registers. SELECT ?legalForm ?companies WHERE { { SELECT ?legalForm (COUNT(?org) AS ?companies) WHERE { GRAPH <https://lindas.admin.ch/foj/zefix> { ?org a <https://schema.ld.admin.ch/ZefixOrganisation> ; schema:additionalType ?legalForm . } } GROUP BY ?legalForm } } ORDER BY DESC(?companies)
{{ template "sparqlAsyncTable" (dict "queryId" "statsZefixLegalForms" "title" (t "card.zefixLegalForms" "Registered entities by legal form") "icon" "building") }}

{{ tHTML "page.statistics.zefixForms" "Three forms account for almost the whole register: the GmbH/Sàrl, the Aktiengesellschaft and the sole proprietorship. Everything else — foundations, associations, cooperatives, partnerships, branches of foreign companies — is a long tail. The presence of foundations and associations is a reminder that this is a register of legal entities, not only of businesses trading for profit." }}

{{ tHTML "page.statistics.zefixJoinIntro" "Because every company records its municipality of domicile as an IRI from the register described above, the two datasets join directly — and counting companies per canton shows something the population figures do not. Zurich leads as expected, but Zug appears far higher than its size warrants: a canton of some 130,000 people hosting tens of thousands of registered entities, which is its low-tax corporate domicile policy made visible in the data." }}

# A genuine CROSS-GRAPH join: the company lives in foj/zefix, the municipality # hierarchy in fso/register, and they meet on the municipality IRI. # # ?canton stays an IRI so the backend resolves and links it. The canton is two hops # from the municipality (via the district) — the same trap noted further up this page. SELECT ?canton ?companies WHERE { { SELECT ?canton (COUNT(?org) AS ?companies) WHERE { GRAPH <https://lindas.admin.ch/foj/zefix> { ?org a <https://schema.ld.admin.ch/ZefixOrganisation> ; <https://schema.ld.admin.ch/municipality> ?municipality . } GRAPH <https://lindas.admin.ch/fso/register> { ?municipality schema:isPartOf ?district . ?district schema:isPartOf ?canton . ?canton a <https://schema.ld.admin.ch/Canton> . } } GROUP BY ?canton } } ORDER BY DESC(?companies)
{{ template "sparqlAsyncTable" (dict "queryId" "statsZefixPerCanton" "title" (t "card.zefixPerCanton" "Registered entities per canton") "icon" "briefcase") }}

{{ tHTML "page.statistics.zefixCaveat" "These are registered entities at their legal domicile, which is not the same as economic activity: a holding company registered in Zug may employ nobody there. Note also that the register carries current entries — it is a snapshot of who exists now, not a history of formations and dissolutions." }}

{{ t "page.statistics.i14y" "The code lists everyone agrees on" }}

{{ tHTML "page.statistics.i14yIntro" "I14Y — the numeronym for interoperability — is the federal platform where agencies publish the code lists they use, so that others can adopt the same ones instead of inventing parallel versions. It is by some distance the largest graph in this theme, and its content is a fair summary of what the Swiss state counts: occupations, diseases, surgical procedures, industries, languages, countries, airports." }}

{{ tHTML "page.statistics.i14yModel" "Everything is modelled in SKOS, the standard vocabulary for classification schemes, with xkos:ClassificationLevel layered on top to mark the rungs of a hierarchy — so a four-digit occupation code knows it sits beneath a three-digit group. Concepts carry their broader and narrower relations, which is what makes a classification usable for aggregation rather than just lookup." }}

# Restricted to version.link Identity schemes on purpose. # # Every scheme exists as an identity PLUS one row per published version (PROFESSIONS # alone has 1.1.0, 1.2.0, 1.2.1, 1.2.2, 1.2.3 …). Without the Identity filter the # table is mostly the same handful of classifications repeated at slightly different # concept counts, which tells you nothing. # # ?scheme is left as a bare IRI and NOT paired with a name column: the backend's # label resolver already renders it as a linked, language-aware title. Selecting # schema:name alongside it produced two near-identical columns — the resolved # English label next to the raw German one. # # Those raw labels all end in "(identity)", an artefact of the versioning model, # which is why showing them directly is worse than letting the resolver do it. SELECT ?scheme ?concepts WHERE { { SELECT ?scheme (COUNT(?c) AS ?concepts) WHERE { GRAPH <https://lindas.admin.ch/fso/i14y> { ?scheme a <https://version.link/Identity> . ?c <http://www.w3.org/2004/02/skos/core#inScheme> ?scheme . } } GROUP BY ?scheme } } ORDER BY DESC(?concepts) LIMIT 60
{{ template "sparqlAsyncTable" (dict "queryId" "statsI14yLargest" "title" (t "card.largestClassifications" "The largest classifications") "icon" "list-tree") }}

{{ tHTML "page.statistics.i14yNames" "The names in that table are worth reading as a list. CH-ISCO-19 is the Swiss occupation nomenclature, the largest thing here at some twenty-five thousand entries. CHOP is the surgical procedure classification and ICD-10-GM the disease classification — both of which every Swiss hospital codes against. NOGA is the industry classification behind business statistics. Between them they are the vocabulary in which the state describes work, illness and the economy." }}

{{ tHTML "page.statistics.i14yCaveat" "I14Y is aggressively versioned: each classification exists as a stable identity plus one concept scheme per published release, and the release schemes are what the raw counts return. The table above filters to identities only. Note also the DV_ prefix on many identifiers — those are the distributed-vocabulary copies, sometimes carrying a slightly different concept count than the original of the same name." }}

{{ t "page.statistics.sharedDimensions" "Shared dimensions" }}

{{ tHTML "page.statistics.territorialIntro" "The territorial graph is small but disproportionately load-bearing. It holds the country, canton and district resources that cube observations across the whole platform point at, plus a set of shared dimensions — ready-made code lists for things that recur across themes: hydropower plants, bathing-water measurement stations, forest-fire warning regions, civil and military aerodromes, biogeographical regions." }}

{{ tHTML "page.statistics.sharedDimensionsWhy" "The point of publishing these centrally is that two offices measuring the same lake, or the same airfield, use the same IRI for it. When the energy theme lists a hydropower plant and the environment theme reports on the river it sits on, the shared dimension is what allows those to be related at all." }}

# ?dim stays an IRI so the backend resolves and links each dimension. # # The name is fetched in its own subquery with SAMPLE: these dimensions carry # de/fr/it/en names WITHOUT consistent tagging across all four, so a plain # ?dim schema:name ?name in the main pattern duplicates every row per language. SELECT ?dim ?terms WHERE { { SELECT ?dim (COUNT(?t) AS ?terms) WHERE { GRAPH <https://lindas.admin.ch/territorial> { ?dim a <https://cube.link/meta/SharedDimension> . ?t schema:inDefinedTermSet ?dim . } } GROUP BY ?dim } } ORDER BY DESC(?terms)
